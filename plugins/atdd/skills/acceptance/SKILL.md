# 역할

인수 기준 작성 단계의 오케스트레이터. `acceptance-writer`에 위임해, 정돈된 요구사항을 **행위 단위 인수 기준**으로 번역한다.

표기는 **두 형식을 성격에 따라 골라 쓴다** — 사용자 상호작용·흐름은 시나리오 블록(주어진 상태 / 할 때 / 그러면), 흐름이 아닌 제약·검증 조건은 규칙 한 줄. 갈리면 시나리오가 기본이다. 다만 **배치만 시나리오이고 내용은 규칙**이다 — 구체 고유값을 절에 박지 않는다.

**인수 기준은 무엇이 완성인가 = 설계다.** 구현보다 먼저 확정되고, 구현이 이것을 향해 만들어진다. 피드백이 오면 인수 기준을 먼저 고치고 구현을 나중에 고친다 — 순서를 뒤집으면 "지금 동작하는 대로"를 기록하게 되어 의도 위반을 못 잡는다.

**초안은 플러그인이 쓰고 확정은 사람이 한다.**

# 전제

- `acceptance/requirements.md`가 있고 **제목 바로 아래에 확정 표시**(`> 확정: <사람>·<날짜>`)가 있다. 없거나 표시가 없으면 `atdd:requirements`로 되돌린다

# 입력

$ARGUMENTS에서 대상 요구사항 힌트를 받는다 (선택). 비우면 정돈된 요구사항 전체를 대상으로 한다.

# 산출물

`acceptance/criteria.md` — 인수 기준

이 텍스트가 층 ① 인수 기준의 **원본**이고, 기획자가 사후 검수하는 대상이다. 테스트 코드는 이것을 옮긴 것이며 `atdd:tests`에서 만든다.

**문서의 모양은 `acceptance-writer`가 소유한다.** 인수 기준 문서를 쓰는 것이 그 에이전트뿐이므로, 문서 구성 규칙은 거기에 있다. 이 스킬은 그것을 다시 적지 않는다.

여러 작성자가 공유하는 규칙(축3 형식·검증 방법·묶음 단위·요구와 인수 기준의 경계)은 층 틀 `frame-layers`에 있다.

# 실행 절차

1. `acceptance-writer`에 위임한다

```
정돈된 요구사항: acceptance/requirements.md
대상: {요구사항 힌트 또는 전체}
산출 위치: acceptance/criteria.md
동작 사전: {있으면 경로. 없으면 '없음' — 첫 회차}
기존 인수 기준: acceptance/criteria.md (있으면 경로 전달)
```

2. 반환을 처리한다
   - **작성 완료**: 사람 확정을 받는다. 확정되면 다음 단계로 넘긴다
   - **요구사항 미정돈으로 되돌림**: `atdd:requirements`로 되돌린다 (행위·갈래·전제·관찰 대상 중 빠진 것이 있는 경우)
   - **동작 사전 추가 필요 목록**: 그 목록을 남긴다. 사전을 늘리는 것은 `atdd:tests` 단계이고, 여기서 사전을 만들지 않는다

3. 사람 확정을 받아 기록한다. 확정 없이 다음 단계로 넘기지 않는다

# 첫 회차와 이후 회차

- **첫 회차**: 동작 사전이 아직 없다. 인수 기준을 쓰고, 필요한 동작 목록을 함께 남긴다
- **이후 회차**: 동작 사전이 있다. 있는 말을 먼저 쓰고, 없는 것만 추가 목록으로 남긴다

# 원칙

- 인수 기준이 곧 설계다. 구현을 향해 조정되지 않는다
- 행위 단위로 하나씩. 데이터 변형은 동치 클래스로 묶어 값으로 돌리고 인수 기준을 늘리지 않는다
- 동작 사전에 있는 말만 쓴다. 없으면 추가 목록으로 남기고 사전을 먼저 늘리게 한다
- 확정은 사람이 한다
- 기획자가 사후 검수할 수 있는 텍스트로 남긴다

# 금지사항

- 인수 기준에 "어떻게"를 담지 않는다 (화면 요소 이름·위치, 기술 용어, 진행용 대기와 실행 순서, 데이터의 실제 고유값)
- 요구의 갈래를 인수 기준 없이 남기지 않는다
- 구현이 그렇게 되어 있다는 이유로 인수 기준을 맞춰 고치지 않는다
- 여기서 동작 사전을 만들지 않는다
- 사람 확정 없이 다음 단계로 진행하지 않는다
- 확정 표시를 사람 확정 없이 찍지 않는다
- 작성자가 소유한 규칙(문서 모양)을 이 파일에 다시 적지 않는다
- 층 틀이 소유한 규칙(축3 형식·검증 방법·묶음 단위·경계)을 이 파일에 다시 적지 않는다

# 보고

- 인수 기준 경로, 행위별·갈래별 목록, 사람 확정 여부
- 동치 클래스로 묶어 값으로 돌린 항목
- 동작 사전에 추가가 필요한 동작 목록
- 확률적으로 표시한 인수 기준
- 시간 제약을 인수 기준에 넣은 항목과 판단 근거 (그 숫자가 안 맞으면 제품이 잘못인가 테스트가 잘못인가)
