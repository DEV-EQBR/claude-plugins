# 이것은 틀이다

세 틀 중 하나. **테스트 하나의 세로 구조**를 정의한다. 이 틀을 정의하는 축은 **축1(인수 기준을 어떻게 뽑나) · 축2(흔들리지 않을 구조) · 축3(무슨 형태로 적나)**이며, 축4의 일부(신뢰성 중 층이 지는 몫)도 여기 꽂힌다.

프로젝트가 이 틀을 채우면 그 프로젝트의 층이 된다. 채우는 것은 작성자들이고, 이 문서는 채워질 모양을 정한다.

# 축 2 — 4계층 (구조 그 자체)

| 층 | 하는 일 |
|---|---|
| **① 인수 기준** (specification) | 무엇이 완성인가(= 설계). 동작 사전의 말만 조합해서 쓴다 |
| **② 동작 사전** (DSL) | 인수 기준이 쓸 수 있는 동작의 이름과 의미. **별칭을 갖는다**(아래) |
| **③ 경로 실행기** (protocol driver) | 그 동작을 특정 경로(문)에서 실제로 수행. 경로마다 하나씩 |
| **④ 검증 대상** (SUT) | 프로젝트의 제품 그 자체. 진입점을 통해서만 접근되고 테스트용 코드가 들어가지 않는다 |

①②③은 테스트 프로그램 쪽, ④는 경계 너머 제품 쪽이다.

## 층 사이의 관계 — 의존은 한 방향(아래로), 각 화살표는 한 종류의 일만

- **소비** (①→②): 인수 기준은 사전에 있는 말만 쓴다. 없으면 사전에 먼저 추가. **요구에도 사전에도 없는 말을 인수 기준이 새로 만들지 않는다** — 그 말이 무엇인지 아무도 확정하지 않은 채 아래 층으로 내려간다
- **위임** (②→③): 사전은 "무엇"만, 실행기가 "어떻게". 동작 하나에 실행기 여럿(경로 수만큼)
- **접근** (③→④): 오직 실행기만 제품에 손댄다. 위 두 층은 제품을 직접 못 건드린다

## 절대 규칙

1. 인수 기준은 **무엇을** 만 담고 **어떻게** 는 담지 않는다
2. 테스트는 제품과 **항상 경로 실행기를 통해서만** 상호작용한다

## 무엇이 문(경로)이고 무엇이 아닌가

경로 실행기가 여는 것을 **문**이라 한다. 문은 제품의 **진입점**이다 — 제품이 바깥에 내주기로 한 자리.

| | 예 |
|---|---|
| **문이다** | 화면 · 공개 API · 그 제품이 내주는 응답 |
| **문이 아니다** | 데이터베이스 · 내부 저장소 · 로그 파일 · 내부 함수 |

**데이터베이스를 관찰 지점으로 삼지 않는다.** 절대 규칙 2를 어긴다 — DB를 직접 읽는 것은 진입점이 아니라 제품 **내부**를 뜯어보는 일이다. 컬럼 하나 바뀌면 제품이 멀쩡한데도 테스트가 깨져, 인수 테스트가 리팩터링을 막는 족쇄가 된다(위 "무엇으로부터 지키는가" — 구현 리팩터링은 인수 기준이 도메인 언어일 것으로 막는다).

**DB를 보고 싶어지면 인수 기준이 덜 다듬어진 신호다.**

| 미달 | `고친 내용이 저장된다` — 무엇을 보면 저장된 것인지 없어서 DB를 열게 된다 |
|---|---|
| 됨 | `고쳐 저장한 뒤 다시 열면 고친 내용이 보인다` — 제품에 다시 물어서 확인한다 |

지속성도 제품에 **다시 물어서** 확인한다. DB는 격리 인프라가 **회차 시작에 바닥을 세울 때만** 다루고, 테스트별 전제는 문을 통해 만든다.

## 문 고르는 규칙 — 하나뿐이다

**볼 수 있는 문 중 가장 싸고 안정적인 문**을 고른다(축 5 경로 선택). 후보가 하나뿐이면 그것이 곧 가장 싼 문이다.

"이 관찰은 이 문으로만 된다"는 강제는 별도 규칙이 아니라 **후보가 하나인 경우**일 뿐이다.

## 무엇으로부터 지키는가 (변화가 층에서 멈춘다)

| 흔드는 것 | 막는 층 |
|---|---|
| 화면 구조 변경 · 테스트 도구 교체 · 진입점 변경 | 경로 실행기 (교체) |
| 구현 리팩터링 · 내부 부품 교체 | 인수 기준이 도메인 언어일 것 |
| 반복 실행의 데이터 충돌 (옆 테스트 · 어제의 회차) | **동작 사전의 별칭** |

요구사항 변화는 방어 대상이 아니다 — 그때는 인수 기준이 바뀌는 것이 정상이다.

## 각 테스트의 실행 흐름 — setup → 검증 → teardown

4층은 검증 순간의 세로 구조다. 각 테스트가 실제로 돌 때는 그 앞뒤에 준비와 정리가 붙는다.

```
setup     → 전제 준비 동작이 돈다 (②→③→④). 별칭으로 **새 것을 만든다**
검증       → 4층이 돎 (①→②→③→④)
teardown  → 없어도 된다 — 치우기는 격리가 아니라 위생이다
```

**전제도 제품의 문으로 만든다.** 격리 인프라를 부르는 것이 아니라, 전제 준비 동작이 사전·실행기를 거쳐 제품에 대고 새 것을 만든다. 이름은 **② 동작 사전이 별칭으로** 고유하게 만들므로 옆 테스트·어제의 회차와 부딪히지 않는다(아래).

격리 인프라는 **회차에 한 번** 바닥을 세우고 물러난다 — 각 테스트의 setup에 끼지 않는다.

# 축 1 — 인수 기준을 어떻게 뽑나 (ATDD)

- 요구사항의 **행위 단위**로 하나씩. 데이터 변형은 인수 기준을 늘리지 않고 값으로 돌린다(동치 클래스)
- 소유자는 **개발자**, 기획자는 요구사항 원천이자 사후 검수자
- **운영 규칙**: 피드백이 오면 인수 기준을 먼저 고치고 구현을 나중에. 순서를 뒤집으면 "지금 동작하는 대로"를 기록하게 되어 의도 위반을 못 잡는다
- 검증 범위는 "잡은 해석대로 구현됐는가"까지. "해석이 맞았는가"는 사후 검수 몫

## 요구와 인수 기준의 경계 — 대상이냐 값이냐

요구 정돈과 인수 기준이 어디서 갈리는지가 이 층의 가장 흔한 혼동 지점이다. 선은 하나다.

| | 요구가 갖는 것 | 인수 기준이 갖는 것 |
|---|---|---|
| **관찰 대상이 있는가** | 여기서 본다 | — |
| **그 대상의 값이 얼마인가** | — | 여기서 정한다 |
| **실패·경계에서 어떻게 되는가** | — | 여기서 정한다 |

- `짧은 칭찬 문구가 보인다` → 관찰 대상이 있다(문구가 보이는지). **요구로 충분하다.** "짧은"의 선은 인수 기준이 정한다
- `자연스럽게 넘어간다` → 관찰 대상이 없다. 무엇을 보는지가 아예 없으므로 **요구 단계에서 고친다**

**임계값·숫자·실패 갈래는 인수 기준의 몫이다.** 요구 정돈이 그것까지 캐물으면 요구사항이 인수 기준의 초안으로 부풀고, 정작 인수 기준 단계는 할 일이 없어진다. 구조도 3이 그 배치를 이미 보여 준다 — 요구사항 상자에는 `가입한 사용자만 로그인할 수 있다` 한 문장뿐이고, **틀린 비번·미가입자라는 실패 갈래는 ① 인수 기준 상자 안에 있다.**

인수 기준은 정상 경로만이 아니라 **오류 조건·경계 상황도 각각 독립된 줄로** 덮는다. 정상 경로 줄에 곁가지로 달지 않는다.

## 요구 하나의 크기 — 사용자가 얻는 능력 하나

요구 하나는 **사용자(또는 어드민)가 얻는 능력 하나**다. 그 능력을 이루는 세부 동작·단계·항목은 요구가 아니라 **인수 기준**이다.

| | 요구 | 인수 기준 |
|---|---|---|
| 단계가 여럿인 흐름 | `여러 단계로 이뤄진 절차를 순서대로 진행한다` **한 줄** | 각 단계가 무엇을 하는지 — 단계 수만큼 |
| 화면에 여러 가지가 보임 | `결과 화면에서 피드백을 보고 다음 행동을 고른다` **한 줄** | 무엇이 보이는지 — 항목마다 |
| 설정이 여럿 | `진행에 걸리는 시간과 횟수를 조절한다` **한 줄** | 어떤 설정이 무엇에 반영되는지 — 설정마다 |

**"한 줄이 한 가지만 말한다"의 '한 가지'는 능력 하나이지 관찰 가능한 사실 하나가 아니다.** 이 구별이 없으면 답을 받을 때마다 쪼개는 것이 항상 옳아 보여서, 요구사항이 인수 기준 크기까지 잘게 부서진다.

## 묶음 단위는 요구다

인수 기준은 **요구 하나에 딸려 붙는다.** 요구가 곧 묶음이다. 주제·영역·화면 같은 다른 기준으로 묶지 않는다 — 그렇게 묶으면 어느 요구가 덮였고 어느 요구가 비었는지 셀 수 없게 된다.

## 입도 신호 — 양쪽 다 본다

요구 하나에 인수 기준 **3~5개**가 보통이다. 양쪽으로 벗어나면 각각 다른 신호다.

| 신호 | 무엇을 뜻하나 | 무엇을 하나 |
|---|---|---|
| 요구 하나에 인수 기준이 **여섯을 넘음** | 요구가 덜 쪼개졌다 | 요구를 나눌 수 있는지 본다 |
| **대부분의 요구가 1:1** | 요구가 과하게 쪼개졌다 — 요구 자리에 인수 기준을 적어 놓은 것이다 | 요구를 능력 단위로 묶는다 |

두 번째가 더 알아채기 어렵다. 각 줄이 다 옳아 보이기 때문이다. 그러나 요구와 인수 기준이 같은 크기면 번역이 아니라 **두 벌 적기**이고, 요구가 바뀔 때마다 두 곳을 고치게 된다.

**제약·표시·금지형 요구는 갈래가 없어 1:1이 정상이다.** 신호로 삼는 것은 흐름·행위형 요구가 1:1이 된 경우다.

## 인수 기준에 들어가면 안 되는 것

- 화면 요소의 이름·위치
- 기술 용어
- 진행용 대기와 실행 순서
- 데이터의 실제 고유값

## 예외 — 요구사항으로서의 시간 제약은 인수 기준에 포함된다

구별법: **"그 숫자가 안 맞으면 제품이 잘못인가 테스트가 잘못인가."** 제품이면 인수 기준, 테스트면 경로 실행기.

성능은 넷을 지킨다: ① 최댓값 대신 백분위(p95·p99) ② 측정 환경 고정 ③ 부하 처리량은 별도 단계로 분리 ④ 측정 경로를 함께 명시.

# 축 3 — 무슨 형태로 적나 (시나리오 + 규칙 조합)

인수 기준은 **두 형식**을 쓴다. 하나로 강제하지 않고 인수 기준마다 성격에 따라 고른다. 한 요구에 둘이 섞여도 된다.

## 고르는 기준

| 형식 | 언제 쓰나 |
|---|---|
| **시나리오 지향** | 사용자 상호작용·흐름. 진입·이탈 지점이 여럿일 때. 이미 복잡한 순서에 새 동작이 끼어들 때 |
| **규칙 지향** | 흐름이 아닌 것. 시스템 수준 제약·검증 조건·표시 금지 사항. 범위가 번지는 것을 막고 싶을 때 |

판단이 갈리면 **시나리오**를 기본으로 한다 — 절이 눈에 보여 다음 층으로 내려갈 자리가 뚜렷하다.

## (가) 시나리오 지향 — 블록

세 절을 **코드 울타리(백틱 세 개)로 감싼다.** 울타리는 예시를 보여주려고 두른 것이 아니라 **산출물에 그대로 들어가는 것**이다 — 절이 줄글에 섞이지 않고 한 덩어리로 보이게 하는 장치다.

아래는 산출물에 들어갈 모양을 글자 그대로 옮긴 것이다. `~~~`로 표기한 자리에 **백틱 세 개**를 쓴다.

```
AC-<n> <제목>
~~~
주어진 상태  <상태>          ← 0개 이상
할 때        <계기>          ← 1개
그러면       <응답>          ← 1개 이상
~~~
```

절 이름과 내용 사이는 공백으로 벌려 세로로 맞춘다. 들여쓰기만 하고 울타리를 빼지 않는다.

## (나) 규칙 지향 — 한 줄 목록

```
AC-<n> <언제나 성립해야 하는 것 한 줄>
```

규칙도 필요하면 상태·계기를 문장 안에 담는다(`<상태>인 동안, <계기>하면, <응답>한다`). 다만 절을 줄로 쪼개지 않는다.

## 인수 기준을 인수 기준이게 하는 것 — 검증 방법이 문장 안에 있다

**모든 인수 기준은 그것이 충족됐음을 확인하는 실행 가능한 테스트 하나 이상에 대응되어야 한다.** 검증 가능성이 주관을 없앤다.

그래서 인수 기준에는 **무엇을 관찰하면 충족인지가 문장 안에 있어야 한다.** 시나리오 지향은 "그러면" 절이 그 자리이고, **규칙 지향도 예외가 아니다** — 통과와 실패가 갈리는 지점이 줄 안에 있어야 하고, 잴 수 있는 것은 수치로 적는다.

| | 예 |
|---|---|
| 미달 | 계정 하나에는 이름이 하나 연결되어 있다 — 무엇을 보면 연결된 것인지 없다 |
| 됨 | 한 세션에서 보이는 이름은 하나뿐이고, 그 세션 내내 바뀌지 않는다 |

## 요구를 어미만 바꿔 옮긴 줄은 인수 기준이 아니다

요구는 **무엇을 원하는가**를 말하고, 인수 기준은 **그것이 충족됐음을 무엇으로 확인하는가**를 말한다. 요구 문장을 그대로 옮기고 어미만 바꾼 줄은 확인 방법을 담고 있지 않으므로 인수 기준이 아니다.

그런 줄이 나오면 둘 중 하나다 — 검증 방법을 붙여 완성하거나, **붙일 수 없다면 그 요구가 검증 불가라는 신호**이므로 요구 정돈으로 되돌린다.

## 배치는 시나리오 모양이되 내용은 규칙이다

**시나리오와 인수 기준은 다른 것이다.** 시나리오는 구체적인 예시이고, 인수 기준은 그 예시들을 낳는 규칙이다.

| | 예 |
|---|---|
| 시나리오 (구체) | 플러피라는 이름의 1.5개월 토끼를 팔려고 하면, 너무 어리다고 알려준다 |
| 인수 기준 (규칙) | 새끼 동물이 판매 권장 연령보다 어릴 때 팔려고 하면, 너무 어리다고 알려준다 |

**우리가 쓰는 것은 규칙이다.** 인수 기준에 데이터의 실제 고유값을 넣지 않고(위 축1 금지 항목), 값 변형은 동치 클래스로 묶어 값으로 돌리기 때문이다. 시나리오 블록 배치를 빌려 쓰되 구체값을 박지 않는다.

## 스텝 정의 결합 금지

시나리오 배치를 쓰더라도 **각 절을 스텝 정의에 1:1로 묶지 않는다.** 테스트는 ②동작 사전의 어휘로 쓴다.

이 금지가 이 축의 핵심이다 — 배치가 아니라 결합이 문제였기 때문이다. 절과 코드가 문자열로 묶이면 요구가 조금 바뀔 때마다 그 연결을 크게 고쳐야 하고, 번역 층만 늘고 검증은 늘지 않는다.

## 절과 층의 대응

| 절 | ② 동작 사전의 갈래 | 테스트에서의 자리 | 실현 |
|---|---|---|---|
| **주어진 상태** (전제) | 전제 준비 동작 | setup | **제품의 문으로 새로 만든다** — 이름은 사전의 별칭이 고유하게 |
| **할 때** (계기) | 검증 행위 동작 | 검증 행위 | 경로 실행기가 수행 |
| **그러면** (응답) | 확인 동작 | 단정 | — |

규칙 지향으로 쓴 인수 기준도 이 셋으로 읽힌다 — 문장 안에 절이 들어 있을 뿐이다.

# 축 4 중 층이 지는 몫

축4 전체 중 **층이 지는 부분만** 여기 있다. 나머지(집계·판정·격리 인프라)는 프로젝트가 자기 방식으로 갖는다.

**세계 1 — 불안정성의 원인이 테스트 쪽에 있다** (같은 코드인데 됐다 안 됐다 한다)

| 규칙 | 어느 층이 |
|---|---|
| 고정 대기 금지 · 상태 대기 | 동작 사전이 상태 대기로 정의하고, 경로 실행기가 그 상태를 실제로 기다린다 |
| 별칭 | **동작 사전이 갖는다.** 아래 「별칭」 참조 |
| 밀폐 데이터 | 각 테스트가 자기 전제를 스스로 준비하고 스스로 치운다. 앞 테스트가 남긴 상태에 기대지 않는다 |
| 순서 의존 금지 | 테스트가 실행 순서를 가정하지 않는다 (순서는 오케스트레이터의 몫) |

**세계 2 — 비결정성의 원인이 제품 쪽에 있다** (제품이 같은 입력에 다른 답을 낸다)

- 문자열 일치 대신 **속성 단언**으로 인수 기준을 쓴다
- 속성으로도 안 되면 골든셋 대상으로 표시한다 — 채점과 임계값 판정은 오케스트레이터의 몫이다

원칙: 잴 수 있는 부분은 결정적으로 만들고 정말 확률적인 부분만 확률로 다룬다.

# 별칭 — 옆 테스트·어제의 회차와 부딪히지 않게

테스트는 **기억하기 쉬운 이름**으로 쓰고, 실제로는 **아무와도 겹치지 않는 이름**이 만들어진다. 둘을 잇는 것이 별칭이며, **이것을 갖는 자리는 ② 동작 사전**이다.

```
테스트가 쓴 것         만들어지는 것
가입한다("김철수")  →  김철수_k3f7_1
                       └──┬──┘ └┬┘
                          │      └─ 회차 안에서 세는 번호 — 동작 사전이 센다
                          └──────── 회차 표 — 밖에서 받는다(회차마다 하나)
```

| 자리 | 무엇을 가르나 |
|---|---|
| **앞 (회차 표)** | 회차가 다르면 앞이 다르다 → **어제 것과 안 겹친다** |
| **뒤 (번호)** | 같은 회차 안에서 하나씩 는다 → **옆 테스트와 안 겹친다** |

- **동작 사전은 회차를 모른다.** 받은 표를 앞에 두고 번호만 센다 — 그래서 회차를 넘겨 기억할 파일이 필요 없다
- **경계가 되는 모든 이름에 붙인다** (계정·기기·물건·이름 등)
- 테스트는 자기가 몇 번인지 **몰라도 된다**
- 회차 표는 **프로젝트가 돌릴 때 만들어 넘긴다.** 그것을 무엇으로 만드는지는 프로젝트의 몫이다

**데이터가 쌓여도 부딪히지 않는다** — 별칭이 있기 때문이다. 그래서 테스트마다 치우는 것은 정확성이 아니라 위생이다.

# 검증 대상이 여럿일 때

이 틀의 나머지는 **검증 대상이 하나**인 것을 전제하고 읽어도 무리가 없다. 제품이 여럿이면(예: 네이티브 앱 + 웹) 두 자리가 갈라진다.

## 층 ② 동작 사전 — 어휘는 하나, 구현은 여럿

테스트가 사는 언어가 갈리면 사전의 **구현**도 언어마다 하나씩 생긴다. 그러나 **어휘(이름과 뜻)는 하나여야 한다** — 같은 말이 두 언어에서 다른 뜻을 가지면 인수 기준 하나가 두 갈래로 갈라져 1:1 대응이 깨진다.

- 어휘 정의는 **언어 중립 문서 한 벌**로 둔다
- 각 언어 구현은 그 문서에 있는 말만 구현한다. 없는 말을 자기 언어에만 추가하지 않는다
- **한 말이 한 언어에만 구현되는 것은 허용된다** — 그 말을 쓰는 인수 기준이 그쪽에만 있으면 된다

## 층 ③ 경로 실행기 — 문은 제품 수와 다르다

한 제품이 문을 여럿 가질 수 있고(화면 + API), 한 문을 여러 곳에서 쓸 수 있다. **문과 제품을 1:1로 보지 않는다.**

특히 **서버 문은 대개 모두가 공유한다** — 화면을 관찰하는 테스트도 전제를 만들 때는 서버 문을 쓴다(축 5: 준비는 싼 문으로).

# 층 ①이 두 벌로 존재한다

인수 기준은 **사람이 확정한 텍스트**(원본 — 시나리오 블록 또는 규칙 줄. 기획자가 사후 검수하는 대상)와 **그것을 옮긴 테스트 코드** 두 벌로 존재한다.

- 텍스트를 쓰는 것은 `acceptance-writer`
- 테스트로 옮기는 것은 `test-writer`
- **둘을 나눈 이유**: 한 주체가 둘 다 쓰면 옮기다 막힐 때 어느 쪽이든 조용히 고쳐 맞출 수 있다. 나눠 두면 옮기는 쪽은 텍스트를 고칠 권한이 없고, "못 옮긴다"고 되돌리는 것만 할 수 있다
- 텍스트와 테스트는 **1:1**이다. 인수 기준 1개 = 테스트 1개. 임의로 합치거나 쪼개지 않는다

# 이 틀을 읽는 작성자

`requirements-facilitator` · `acceptance-writer` · `dictionary-writer` · `driver-writer` · `test-writer`

요구 정돈 작성자는 이 틀에서 **요구와 인수 기준의 경계 · 요구 하나의 크기 · 입도 신호 · 축1**을 읽는다. 요구사항 문서의 모양은 그 작성자가 자기 안에 갖는다 — 그것을 쓰는 작성자가 하나뿐이기 때문이다.

각 작성자는 자기 층의 규칙을 여기서 읽고, 자기 안에 규칙을 다시 적지 않는다. 이 틀이 바뀌면 작성자를 고치지 않고 여기만 고친다.
