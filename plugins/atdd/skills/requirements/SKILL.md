# 역할

요구사항 정돈 단계의 오케스트레이터. `requirements-facilitator`에 위임해, 들어온 요구를 **인수 기준으로 번역될 수 있는 상태**까지 정돈한다.

이 단계가 있는 이유는 하나다 — 요구는 난잡하게 들어오고, 요구를 말하는 사람도 자기가 무엇을 원하는지 정확히 모르는 경우가 많다. 그 상태로 번역에 넘기면 번역하는 쪽이 빈칸을 해석으로 메운다.

**이 단계는 보조다.** 요구사항의 원천과 확정은 사람이 소유한다.

# 전제

- 요구가 들어왔다. 형태·완성도는 상관없다

# 입력

$ARGUMENTS의 요구사항. 비었으면 사람에게 요구를 받는다.

# 산출물

`acceptance/requirements.md` — 정돈된 요구사항.

**문서의 모양은 `requirements-facilitator`가 소유한다.** 요구사항 문서를 쓰는 것이 그 에이전트뿐이므로, 문서 구성·요구를 적는 형태·주체별 묶음 규칙은 전부 거기에 있다. 이 스킬은 그것을 다시 적지 않는다.

여러 작성자가 공유하는 규칙(요구와 인수 기준의 경계·요구 하나의 크기·입도 신호·축1)은 층 틀 `frame-layers`에 있고, 작성자가 직접 읽는다.

# 실행 절차

1. `requirements-facilitator`에 위임한다

```
요구사항: {들어온 요구 그대로}
산출 위치: acceptance/requirements.md
기존 요구사항: acceptance/requirements.md (있으면 경로 전달)
```

2. 반환을 처리한다
   - **되물을 항목이 있음**: 그 목록을 사람에게 전달해 답을 받고, 답을 들고 다시 위임한다
   - **정돈 완료(사람 확정)**: 다음 단계(`atdd:acceptance`)로 넘길 수 있다
   - **관찰 불가로 남은 항목 있음**: 그 사실을 사람에게 알린다. 관찰할 수 없는 요구는 인수 기준이 될 수 없으므로, 확정하지 않고 남긴다

3. 요구에서 떼어 낸 구현 방법 서술이 있으면 사람에게 함께 보고한다 — 요구가 아니므로 인수 기준에 넣지 않는다

# 원칙

- 사람이 확정하지 않은 것을 확정으로 넘기지 않는다
- 여기서 인수 기준을 쓰지 않는다 — 행위 단위 분해와 시나리오/규칙 표기는 다음 단계다
- 요구를 임의로 늘리거나 줄이지 않는다. 갈래를 발견해 제안하는 것과 요구를 새로 만드는 것은 다르다
- 되물을 것을 추론으로 메우지 않는다

# 금지사항

- 인수 기준을 작성하지 않는다
- 작성자가 소유한 규칙(문서 모양·요구를 적는 형태·주체별 묶음)을 이 파일에 다시 적지 않는다
- 층 틀이 소유한 규칙(경계·입도·축1)을 이 파일에 다시 적지 않는다
- 사람 확정 없이 다음 단계로 진행하지 않는다
- 확정 표시를 사람 확정 없이 찍지 않는다

# 보고

- 정돈된 요구사항 경로와 사람 확정 여부
- 드러난 넷 요약 (검증 행위 · 갈래 수 · 전제 · 관찰 대상)
- 추론으로 채운 항목
- 되물었으나 못 채운 항목
- 요구에서 떼어 낸 구현 방법 서술
