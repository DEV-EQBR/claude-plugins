# 이 플러그인이 무엇인가

**인수 테스트 시스템 = 규칙·정책 한 벌.** 축 1~5가 세 틀을 정의하고, 그 세 틀이 각 프로젝트의 테스트 프로그램을 정의한다. 프로젝트는 그 틀을 채워 자기 프로그램을 갖고, 그 프로그램이 자기 제품을 검증한다.

## 층 틀 — 규칙 (항상 있다, 프로젝트가 들어오기 전 확정됨)

| 틀 | 무엇을 정의하나 | 꽂히는 축 |
|---|---|---|
| `frame-layers` | 테스트 하나의 세로 구조 — 인수 기준 · 동작 사전 · 경로 실행기 · 제품 | 축 1 · 2 · 3 (+4 일부) |

## 세 단계 — 그 틀을 채우는 순서

```
① atdd:requirements   요구 정돈        → 정돈된 요구사항 (사람 확정)   ※ 층 밖 (추가 구간)
      ▼
② atdd:acceptance     인수 기준 작성    → 인수 기준 (사람 확정)         ※ 층 ①의 원본
      ▼
③ atdd:tests          테스트 만들기     → 동작 사전 · 테스트 · 실행기    ※ 층 ①②③
```

**이것은 만드는 순서이지 테스트를 돌리는 것이 아니다.** 테스트를 돌리는 것은 **프로젝트가 갖는 오케스트레이터**이고, 제품을 알려진 상태로 띄우는 것은 **프로젝트가 갖는 격리 인프라**다. 둘 다 이 플러그인이 만들지 않는다.

# 전제 — 프로젝트가 먼저 갖춰야 하는 것

이 파이프라인은 **기반 위에서 돈다.** 기반은 프로젝트가 자기 방식으로 세운다 — 언어·도구·배포가 프로젝트마다 달라 규칙으로 강제할 수 없다.

| 무엇 | 하는 일 |
|---|---|
| **격리 인프라** | 회차에 한 번 바닥을 세우고 제품을 알려진 상태로 띄우고 경계 가짜를 배선한다 |
| **오케스트레이터** | 모아 돌리고 집계하고 이력을 남긴다. 회차 표를 만들어 층에 넘긴다 |
| **층 셋을 둘 자리** | 동작 사전 · 테스트 · 경로 실행기가 살 곳과 돌리는 명령 |

무엇이 필요한지는 SoT(`docs/acceptance-test-system/atdd.html`)에 있다. 프로젝트가 그것을 읽고 세운다.

# 끝점 — 무엇이 완성인가

이 파이프라인이 끝나면 프로젝트 안에 **층 셋이 채워져 돌 수 있다.** 제품이 아직 없으면 돌렸을 때 테스트가 실패한다 — **그것이 정상 종료 상태다.**

제품(검증 대상)과 기반은 이 범위 밖이다.

# 회차에 따른 진행

| 회차 | 진행 |
|---|---|
| **첫 회차** (프로젝트에 기반이 없음) | ① → ② → ③ → ④ |
| **이후 회차** (요구가 추가됨) | ① → ② → ④ (기반은 이미 있음) |

기반은 프로젝트가 이미 갖고 있어야 한다. 없으면 사람에게 알리고 멈춘다 — 여기서 만들지 않는다.

# 입력

$ARGUMENTS의 요구사항. 비었으면 사람에게 받는다.

# 실행 절차

각 단계를 순서대로 호출하고, 반환을 처리한 뒤 다음으로 넘어간다.

1. `atdd:requirements` 호출
   - 되물을 항목이 있으면 사람에게 전달하고 답을 받아 다시 진행한다
   - **사람 확정 없이 ②로 넘어가지 않는다**
   - 관찰 불가로 남은 요구가 있으면 사람에게 알리고, 그 요구는 확정하지 않는다

2. `atdd:acceptance` 호출
   - 요구사항 미정돈으로 되돌아오면 ①로 되돌린다
   - **사람 확정 없이 ③·④로 넘어가지 않는다**

   - 미결(이력 저장소 위치 · 축4 숫자)의 처리 결과를 기록한다

4. `atdd:tests` 호출
   - 인수 기준이 모호하다고 되돌아오면 ②로 되돌린다
   - 격리 인프라를 손봐야 했으면 그 사실을 기록한다
   - 제품 진입점 부재로 막히면 사람에게 보고한다

5. 마지막에 한 번 돌려 상태를 확인하고 보고한다

# 되돌림 규칙

되돌림은 **한 칸 위로만** 한다. 아래에서 지어내지 않는다.

| 무엇이 부족한가 | 어디로 |
|---|---|
| 요구가 정돈되지 않음 (행위·갈래·전제·관찰 대상 중 빠짐) | ① |
| 인수 기준이 모호해 단정 확정 불가 | ② |
| 이력 저장소 등 기반이 없음 | 사람에게 알리고 멈춘다 |
| 동작 사전에 말이 없음 / 동작 정의가 모호함 | ④ 안에서 사전을 고친다 |
| 제품 진입점이 없음 | 사람에게 보고 (제품을 고칠 일) |

# 원칙

- 사람이 확정해야 하는 두 지점(정돈된 요구사항 · 인수 기준)에서 확정 없이 다음으로 넘어가지 않는다. 확정은 각 파일 제목 바로 아래의 확정 표시(`> 확정: <사람>·<날짜>`)로 확인하며, 그 표시를 대신 찍지 않는다
- 층 셋을 둘 자리와 돌리는 명령은 **프로젝트가 알려 준다.** 프로젝트를 뒤져 추측하지 않는다
- 단계를 건너뛰지 않는다. ③은 회차 판단으로만 생략한다
- 부족한 것을 아래 단계에서 지어내지 않는다 — 한 칸 위로 되돌린다
- 제품이 없어 테스트가 실패하는 것은 정상 종료 상태다. 통과하게 만들려고 손대지 않는다
- 테스트를 돌리는 것은 프로젝트 오케스트레이터다. 이 스킬이 대신 판정하지 않는다
- 규칙은 세 틀에 있다. 단계가 규칙을 자기 안에 다시 적지 않는다

# 금지사항

- 사람 확정을 건너뛰지 않는다
- 인수 기준을 테스트나 구현에 맞춰 고치지 않는다
- 테스트를 통과시키려고 단정을 완화하지 않는다
- 제품(④)을 만들지 않는다 — 이 범위 밖이다
- 미통과 시 차단(게이트)을 만들지 않는다 — 범위 밖이다

# 보고

- 진행한 단계와 각 단계 산출물 경로
- 사람 확정을 받은 두 지점의 확정 여부
- 인수 기준 ↔ 테스트 1:1 대조 결과
- 세운 기반 요약 (첫 회차인 경우) — 격리 인프라 / 오케스트레이터
- **마지막 실행 결과** — 수집된 테스트 수, 실패가 단정 미충족인지, 못 도는 테스트가 있는지, 집계·이력·보고 작동 여부
- 되돌린 항목과 사유
- 미결로 남은 것 (이력 저장소 위치 · 축4 숫자 · 관찰 불가 요구 · 진입점 부재 · **격리 못 한 것** 등)
