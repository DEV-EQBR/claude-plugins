# 역할

테스트 만들기 단계의 오케스트레이터. 세 틀 중 **층 틀**을 프로젝트 안에 채우고, 그 과정에서 새로 걸린 격리 대상을 등록한다. 네 에이전트에 순서대로 위임한다.

**인수 기준이 늘 때마다 반복한다.** 사전·실행기는 있는 것을 재사용하고 없는 것만 늘린다.

# 순서와 그 이유

```
① 동작 사전        어떤 말이 필요한가 (전제 준비 / 검증 행위 / 확인)
      ▼             → 전제 준비가 격리에 요청할 것이 드러난다
② 테스트           인수 기준을 사전의 말만으로 옮긴다
      ▼             → 사전에 무엇이 부족한지, 실행기가 무엇을 해내야 하는지가 드러난다
③ 경로 실행기       그 말을 어느 문에서 어떻게 수행하나 (문이 늘 때마다 늘어남)
      ▼             → 실행기가 격리에 요청할 것(포트·복제본 등)이 드러난다
```

**테스트가 실행기보다 먼저인 이유**: 테스트는 **사전에 있는 말의 이름만** 있으면 쓸 수 있고, 그 말이 실제로 어떻게 수행되는지는 몰라도 된다. 오히려 테스트를 먼저 써야 **사전에 무엇이 부족한지**가 드러나고 **실행기가 무엇을 해내야 하는지**가 확정된다.

실행기를 먼저 만들면 순서가 뒤집힌다 — **실행기가 할 수 있는 것에 맞춰 테스트를 쓰게 된다.** 제품에 맞춰 인수 기준을 고치는 것과 같은 병이다(축 1 운영 규칙 위반).

일반 ATDD도 같은 순서다 — 명세와 사전이 먼저, 실행기가 그다음, 제품이 마지막.

**①과 ②는 붙어 있다.** 테스트를 쓰다 말이 없으면 사전으로 돌아가고, 사전을 늘리면 다시 테스트로 온다. 왔다 갔다 하다 굳는다.

**격리 인프라는 여기서 손대지 않는다.** 그것은 프로젝트가 자기 방식으로 갖는 기반이고, 이 단계의 범위 밖이다. 다만 층을 채우다 **새 외부 의존이 생겼거나 별칭으로 못 가르는 것이 걸리면** 보고한다 — 기반을 손볼지는 프로젝트가 정한다.

# 전제

- `acceptance/criteria.md`가 있고 **제목 바로 아래에 확정 표시**(`> 확정: <사람>·<날짜>`)가 있다. 표시가 없으면 `atdd:acceptance`로 되돌린다 — 확정되지 않은 인수 기준을 테스트로 옮기지 않는다
- **프로젝트에 기반이 서 있다** — 제품을 알려진 상태로 띄우는 격리 인프라, 모아 돌리고 집계하는 오케스트레이터, 그리고 층 셋을 둘 자리. 없으면 사람에게 알리고 멈춘다

**기반은 이 플러그인이 만들지 않는다.** 프로젝트마다 언어·도구·배포가 달라 규칙으로 강제할 수 없다. 무엇이 필요한지는 SoT(`docs/acceptance-test-system/atdd.html`)의 오케스트레이터·격리 인프라 절에 있고, 프로젝트가 그것을 읽고 자기 방식으로 세운다.

**자리는 프로젝트가 알려 준다.** 층 셋(동작 사전·경로 실행기·테스트)을 어디에 둘지, 무엇으로 돌릴지를 받아서 쓴다. 못 받으면 묻는다 — 프로젝트를 뒤져 추측하지 않는다.

# 입력

$ARGUMENTS에서 대상 인수 기준 힌트를 받는다 (선택). 비우면 테스트가 아직 없는 인수 기준 전체를 대상으로 한다.

# 실행 절차

## 1단계: 동작 사전

`dictionary-writer`에 위임한다.

```
인수 기준: acceptance/criteria.md
대상: {인수 기준 힌트 또는 테스트 없는 전체}
기존 동작 사전: {있으면 위치}
```

반환에 **실행기가 필요한 새 동작 목록**과 **별칭을 붙인 이름 목록**이 담긴다.

## 2단계: 테스트

`test-writer`에 위임한다. **경로 실행기는 아직 없다** — 테스트는 사전의 말 이름만으로 쓴다.

```
인수 기준: acceptance/criteria.md (사람 확정 원본 — 고치지 않는다)
대상: {인수 기준 힌트 또는 전체}
동작 사전: {동작 사전 위치}
경로 실행기: 아직 없다 — 사전의 말 이름만으로 옮긴다
```

반환에 **사전에 없어서 못 옮긴 것**이 담긴다. 그러면 1단계로 돌아가 사전을 늘리고 다시 온다 — 이 왕복이 정상이다.

**여기서 돌려 보지 않는다.** 실행기가 없어 아직 돌 수 없다. 도는 것은 4단계 뒤다.

## 3단계: 경로 실행기

`driver-writer`에 위임한다.

```
동작 사전: {동작 사전 위치}
테스트: {테스트 위치} — 어느 말이 실제로 쓰이는지
인수 기준: acceptance/criteria.md — 각 인수 기준을 어느 문으로 보는지
기존 격리 인프라: {격리 인프라 위치}
기존 실행기: {실행기 위치, 있으면}
필요한 동작: {1·2단계가 넘긴 실행기 필요 동작 목록}
```

문이 이미 있으면 그 실행기를 늘리고, 새 문이 필요할 때만 새로 만든다. **실행기는 가짜를 모른다** — 프로젝트의 격리 인프라가 이미 배선해 두었다. 인수 기준이 바깥의 실패·지연을 관찰할 때만 가짜의 문을 하나 더 만든다.

## 4단계: 되돌림 처리

| 되돌림 | 처리 |
|---|---|
| 인수 기준 텍스트가 모호해 단정 확정 불가 | `atdd:acceptance`로 되돌린다 — 여기서 조여 만들지 않는다 |
| 동작 사전에 말이 없음 | 1단계로 돌아가 사전을 늘린다 |
| 동작 정의가 모호해 경로마다 결과가 달라짐 | 1단계로 돌아가 사전을 고친다 |
| 별칭으로 못 가르는 것이 걸림 | **보고한다** — 기반을 손볼지는 프로젝트가 정한다 |
| 제품에 가짜를 꽂을 자리가 없음 | **훅을 뚫지 않고 보고한다** — 그 인수 기준은 격리되지 않은 채 돈다고 표시한다 |
| 제품 진입점이 없어 실행기가 막힘 | 사람에게 보고한다 — 제품을 고칠 일이지 실행기가 우회할 일이 아니다 |

## 5단계: 돌려 본다

프로젝트의 오케스트레이터로 돌린다. 여기서 처음으로 사슬 전체가 돈다.

확인할 것은 셋이다.

- 오케스트레이터의 **수집**이 새 테스트를 발견했는가
- 각 테스트가 **"단정이 충족되지 않음"으로 실패/통과**하는가 — 테스트 자체가 못 도는 것(문법·연결 오류)은 미완성이므로 고친다
- **집계·이력 기록·보고**가 작동했는가

**결과를 어떻게 읽나는 제품이 있느냐에 달렸다.**

| 제품이 | 정상 상태 |
|---|---|
| **아직 없다** | 전부 실패한다. 실패가 "단정 미충족"이면 정상이다 |
| **이미 있다** | 일부는 통과하고 일부는 실패한다. **전부 실패가 정상이 아니다** |

제품이 있을 때의 실패는 둘 중 하나이고, **가르는 것은 사람이다.**

- **제품이 인수 기준과 다르다** → 제품을 고친다
- **인수 기준의 해석이 제품 의도와 달랐다** → **인수 기준을 먼저 고치고** 구현을 나중에 (축 1 운영 규칙)

어느 쪽이든 **테스트를 통과시키려고 단정을 완화하지 않는다.**

# 원칙

- 인수 기준 텍스트는 사람이 확정한 원본이다. 테스트를 맞추려고 고치지 않는다 — 모호하면 되돌린다
- 인수 기준 1개 = 테스트 1개를 유지한다
- 사전에 있는 말만 테스트에 쓴다. 없으면 사전을 먼저 늘린다
- 있는 사전·실행기를 재사용한다
- 걸리지 않는 격리 대상을 미리 등록하지 않는다
- **결과를 읽는 법은 제품이 있느냐에 달렸다** (6단계 표). 못 도는 것(문법·연결 오류)은 어느 경우든 미완성이다

# 금지사항

- 인수 기준 텍스트를 이 단계에서 고치지 않는다
- 인수 기준에 없는 단정을 테스트에 추가하지 않는다
- 인수 기준 하나를 여러 테스트로 쪼개거나 여럿을 하나로 합치지 않는다
- 동작 사전에 없는 말을 테스트에 쓰지 않는다
- 제품에 테스트용 코드를 넣지 않는다
- 제품 진입점이 없을 때 우회로를 만들어 통과시키지 않는다 — 보고한다
- 고정 대기를 쓰지 않는다
- 데이터의 실제 고유값을 테스트에 박지 않는다 — 별칭을 쓴다
- **테스트를 통과시키려고 단정을 완화하지 않는다**
- **테스트가 늘었다는 이유로 격리 인프라를 늘리지 않는다** — 별칭이 이미 막는다
- 테스트마다 환경을 갈아엎는 것을 만들지 않는다
- 병렬 실행을 전제하지 않는다

# 보고

- 만든 테스트 목록과 대응 인수 기준 (1:1 대조 — 누락 0 / 임의 추가 0)
- 늘린 동작 사전 (갈래별)
- 격리를 손봤는지 — 손봤으면 무엇이 새로 흔들렸는지, 안 손봤으면 없다고 명시
- **격리 못 한 것** — 제품에 꽂을 자리가 없어 격리 안 된 채 도는 인수 기준
- 만든·늘린 경로 실행기 (경로별), 가짜로 대체한 외부 서비스와 근거
- 붙인 태그
- 확률적 처리 항목 (속성 단언 / 골든셋 대상)
- **첫 실행 결과** — 수집된 테스트 수, 통과/실패 내역, 못 도는 테스트가 있는지, 집계·이력·보고 작동 여부.
  제품이 이미 있으면 **실패마다 '제품이 다름'인지 '해석이 달랐음'인지 사람이 가를 수 있게** 근거를 함께 낸다
- 되돌린 항목과 사유
